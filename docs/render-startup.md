# Render startup and health checks

## Deploy this repository

Existing store deployment: frontend `https://sekjad.com`, backend `https://bkd.sekjad.com`, frontend API base `https://bkd.sekjad.com/api/v1`. Set both `BASE_URL` and `FRONTEND_ORIGIN` to `https://sekjad.com` in the existing Render service. Verify readiness at `https://bkd.sekjad.com/health`.

The root `render.yaml` defines a Node web service on `main`, tests each build before pruning development dependencies, and checks `/health`. `.node-version` pins the runtime used in local verification and CI. Remove any conflicting `NODE_VERSION` override in Render.

1. Commit and push the production fixes and deployment files to GitHub (`Izzyzero/sekjad-backend`). Render cannot deploy uncommitted local files.
2. For a new service, open Render **New > Blueprint**, select the repository, and review the service plan and region before creating it. The Blueprint leaves the compute plan unspecified, so Render chooses its default paid web-service plan for a new service. Select the plan you intend to use before confirming.
3. Enter the prompted environment values privately in Render. `BASE_URL` must be your frontend's exact HTTPS origin (no trailing slash or path), not the backend URL. Use the MongoDB Atlas connection URI for `MONGO_URI`. JWT secrets are generated by Render. `MAIL_FROM` must be a verified Resend sender; `CONTACT_TO` is the inbox receiving contact messages.
4. Allow the Render service's outbound IP ranges in MongoDB Atlas Network Access, then deploy. Keep the app at one instance until a shared rate-limit store is configured.
5. Check `https://<your-service>.onrender.com/health` for HTTP 200 and `{"status":"ok"}`. Set the frontend's API base URL to `https://<your-service>.onrender.com/api/v1` and verify the real authentication and checkout flows.

For an existing service, update its settings instead of creating another service: branch `main`, build command `npm ci --include=dev && npm test && npm prune --omit=dev`, start command `npm start`, health check `/health`. Preserve its existing production secrets and configure the required environment values below. If enabling Google login, add `GOOGLE_CLIENT_ID`; the Blueprint defaults to WhatsApp checkout.

For browser sessions, use frontend and API domains under the same site, such as `www.example.com` and `api.example.com`. The current `SameSite=Lax` cookie does not support unrelated frontend/backend sites for refresh requests.

Blueprint documentation: https://render.com/docs/blueprint-spec

Use `npm ci --include=dev && npm test && npm prune --omit=dev` as the build command and `npm start` as the start command. Set `NODE_ENV=production` and set the Render Health Check Path to `/health` under Settings → Health Checks. Render supplies `PORT`; the server binds to `0.0.0.0`, defaulting to port 10000 locally.

Startup validates configuration, then waits up to 10 seconds for MongoDB server selection before opening the HTTP listener. Failures exit with status 1 and log a sanitized message.

Required environment variables:
- `MONGO_URI`
- `ACCESS_TOKEN_SECRET`, `REFRESH_TOKEN_SECRET`: different secrets, each at least 32 characters in production
- `SALT`: integer bcrypt cost from 4 to 15
- `BASE_URL`: frontend URL, HTTPS in production; optional `FRONTEND_ORIGIN` must also be valid
- `CLOUD_NAME`, `CLOUD_API_KEY`, `CLOUD_API_SECRET`
- `RESEND_API_KEY`, `MAIL_FROM` (a sender on your verified Resend domain)
- `WHATSAPP_ORDER_NUMBER` when Paystack is disabled (the default)
- `PAYSTACK_SECRET_KEY` when `PAYSTACK_ENABLED=true`

Google sign-in is optional: set `GOOGLE_CLIENT_ID` to enable it; no OAuth client secret is needed for the current flow. Optional token durations and OTP settings are validated when supplied. Configuration validation checks presence and format, not whether external credentials are accepted. Email uses the Resend HTTPS API; SMTP ports are not needed. See [Resend setup](resend-email.md).

`GET /health` requires no authentication, disables caching, and returns `{ "status": "ok" }` with HTTP 200 only after a successful MongoDB ping. Disconnection, ping failure, a two-second timeout, or shutdown returns HTTP 503 with `{ "status": "unavailable" }`. Database details are never exposed. `/` remains a welcome endpoint.

On SIGTERM/SIGINT, readiness is disabled, the listener closes, active requests drain, and MongoDB disconnects. The process exits successfully when cleanup finishes. A 25-second deadline forces exit with status 1 if cleanup hangs. New requests reaching an existing connection while shutting down receive 503.

Validate with `npm test`. This runs JavaScript and CommonJS test files with test credentials and local HTTP listeners; database behavior is mocked. GitHub Actions runs the tests and production dependency audit on pushes and pull requests. After deployment, check `/health` and exercise real login, email and upload flows.

References: [Render health checks](https://render.com/docs/health-checks), [Render deployment lifecycle](https://render.com/docs/deploys).

## Proxy trust and rate limits

Proxy trust is configured before routes and rate limiters. When Render sets `RENDER=true`, the default is one trusted hop. Outside Render, the default is zero (direct connections; forwarded headers are ignored). Set `TRUST_PROXY_HOPS=1` explicitly for a verified single-hop ingress path, or override with the verified count for your infrastructure. Only integers from 0 through 10 are accepted; blanket `true` is rejected.

The one-hop default is an assumption, not a live verification of your deployment. Before launch, confirm Express's `req.ip` matches the client on requests through the real ingress, including custom domains/CDNs. Use temporary restricted diagnostics or server logs; do not leave a public diagnostic endpoint enabled. Verify clients on separate networks receive independent rate limits. Do not increase the hop count blindly: all reachable paths must have the expected trusted hops, and the ingress must sanitize forwarded headers. See [Express proxy guidance](https://expressjs.com/en/guide/behind-proxies/) and [rate-limit troubleshooting](https://github.com/express-rate-limit/express-rate-limit/wiki/Troubleshooting-Proxy-Issues).

Rate-limit storage remains per-process memory. Multiple instances require a shared store for globally consistent limits. Upload limits remain keyed by authenticated admin ID.

## Production release checks

Use a single application instance until a shared rate-limit store is configured. Terminate HTTPS at the ingress and redirect HTTP to HTTPS. Set `NODE_ENV=production`; refresh cookies then require HTTPS. The API sends HSTS, no-sniff, frame-denial, no-referrer, and no-store headers.

Refresh cookies use `SameSite=Lax`. Host the frontend and API on the same site (for example `www.example.com` and `api.example.com`), and send credentialed browser requests. If they must use unrelated domains, design and test a cross-site cookie and CSRF policy before switching to `SameSite=None`.

Before accepting real customers:

- Run `npm ci`, `npm test`, and `npm audit --omit=dev` on the release revision.
- Confirm production secrets and provider credentials in the hosting environment; never commit `.env`.
- Enable MongoDB backups and perform a restore drill; verify required unique and TTL indexes exist, including users, orders, OTPs, and refresh sessions.
- Configure uptime monitoring for `/health`, error alerts, log retention, and a rollback procedure.
- In staging, exercise registration, email verification, login/refresh/logout, password reset, admin uploads, checkout, and order confirmation using real integrations and test accounts.
- If enabling Paystack, test signed webhooks, duplicate delivery, verification, and reconciliation against provider records. Initialize requests create independent transactions; do not automatically retry them after ambiguous network failures.
- Verify proxy IP handling and rate limits through the deployed ingress, then load-test expected traffic.

These operational checks require access to the deployed infrastructure; local tests do not certify them.
